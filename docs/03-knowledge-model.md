# 3. Knowledge model

Status: proposal for review. Field names may still change before Phase 3 freezes them in JSON Schema.

## 3.1 Principles

1. **Layers are kept apart.** Original source material, Sina-authored records, AI-generated content, relationships, embeddings, personal data and admin data are stored separately and never overwrite each other.
2. **Every record has a permanent ID.** IDs are never reused. When records are merged or renamed, the old ID redirects.
3. **Everything says where it came from.** Each record and relationship carries its origin and, where it exists, the exact slide or page.
4. **Nothing AI-generated is presented as verified** until an administrator has approved it.

## 3.2 Layers

| Layer | Contents | Stored in |
|---|---|---|
| Sources | Original files and their pages or slides | `kb/sources/` |
| Records | Normalised knowledge items | `kb/records/` |
| AI artifacts | Summaries, classifications and extractions produced by a model | `kb/ai/` |
| Relations | Typed links between records | `kb/relations/` |
| Embeddings and indexes | Derived, rebuildable | Build output, not committed |
| Admin | Manifest, ingestion state, audit log, ID registry | `kb/admin/` |
| Personal | Notes, bookmarks, tasks, annotations, progress | The user's browser (IndexedDB) |

## 3.3 Stable identifiers

An ID is `<type>:<key>`. Imported records derive the key from Sina so that the two systems can refer to each other without a lookup service.

| Record type | ID pattern | Example | Derived from |
|---|---|---|---|
| Program | `prog:<id>` | `prog:y2-anglo` | `SINA.programs` |
| Subject | `subj:<id>` | `subj:anat3` | `SINA.subjects` |
| Module (Sina "group") | `mod:<subject>/<slug>` | `mod:anat3/neuroanatomy` | Group name, slugged once and recorded |
| Lecture | `lec:<id>` | `lec:anat3-larynx` | Sina lecture ID |
| Summary section | `sec:<lecture>/<id>` | `sec:physio-pain/def` | `summary[].id` |
| Slide | `slide:<lecture>/<nn>` | `slide:physio-pain/04` | Slide file name |
| Source file | `src:<sha256-prefix>` | `src:9f2c41d07a3e` | Hash of the file's bytes |
| MCQ | `q:<key>` | `q:1incxx9` | Sina's alias-resolved question key |
| Flashcard | `card:<lecture>/<id>` | `card:physio-pain/p1` | Sina card ID |
| Past paper | `paper:<id>` | `paper:anat3-sina-mock-1` | Sina paper ID |
| External resource | `res:<hash>` | `res:5k2m9x` | Hash of the normalised URL |
| 3D model | `m3d:<id>` | `m3d:larynx` | `SINA.m3d` |
| Concept | `c:<slug>` | `c:allodynia` | Minted by the pipeline, recorded in the registry |
| Clinical case, document, other | `<type>:<minted>` | `case:0001` | Minted |

Rules:

- **Question keys.** The key is Sina's hash after applying `qalias.js`, so it matches the key under which Sina stores progress. The same question appearing in several papers is one record with several "appears in" relations.
- **Registry.** `kb/admin/id-registry.jsonl` lists every ID ever issued, with `created`, `status` (`active`, `merged`, `retired`) and `redirect` when merged. The importer fails loudly if a previously seen Sina question disappears without an alias, instead of silently creating a new record.
- **Concept slugs** are lowercase ASCII with hyphens. Synonyms live in the concept's `aliases`, not in the ID.

## 3.4 Record

Common fields for every record:

| Field | Type | Notes |
|---|---|---|
| `id` | string | As above |
| `type` | string | See 3.5 |
| `title` | string | |
| `description` | string, optional | One or two sentences |
| `body` | object, optional | Type-specific original content (e.g. question stem and options, section HTML) |
| `origin` | `original` · `sina` · `ai` · `admin` | Who produced the content. `original` = taken from a source file; `sina` = authored for the Sina site; `ai` = generated by the pipeline; `admin` = written by an administrator in Brain |
| `status` | `proposed` · `approved` · `rejected` · `retired` | Only `approved` records are published |
| `verification` | `unverified` · `checked-against-source` · `expert-reviewed` | Separate from `status`; shown to students |
| `subject`, `module`, `lecture` | IDs, optional | Primary placement in the hierarchy |
| `tags`, `keywords` | string arrays | |
| `provenance` | array | Each entry: `{source, unit?, locator?, note?}` pointing to a source file and slide or page |
| `ext` | object | External identifiers: `sina`, and optionally `mesh`, `wikidata` |
| `created`, `updated` | ISO dates | |
| `rev` | integer | Incremented on each change |

AI-produced additions (summary, classification, keywords, confidence) are **not** fields on the record. They live in the AI artifact layer and are joined at build time, so regenerating them can never damage original content.

## 3.5 Record types

Hierarchy: `program`, `subject`, `module`, `lecture`, `section`.

Sources: `source` (file), `slide` (page or slide of a source).

Knowledge: `concept`, with a `kind` field: `structure` (anatomy), `process` (physiology), `condition` (pathology), `drug`, `organism`, `sign-symptom`, `investigation`, `procedure`, `principle`, `other`.

Assessment: `mcq`, `flashcard`, `paper`.

Media and reference: `figure`, `model3d`, `occlusion`, `resource` (external link), `document`, `article`, `case`.

New types are added by adding a schema file; nothing else in the model depends on the list being closed.

Personal types (`note`, `idea`, `task`, `bookmark`, `collection`, `annotation`, `plan`) use the same field conventions but exist only in the personal store.

## 3.6 Concept

In addition to the common fields:

| Field | Notes |
|---|---|
| `kind` | See 3.5 |
| `aliases` | Synonyms, abbreviations, eponyms, alternative spellings |
| `definition` | Short definition, with its own `origin` and `provenance` |
| `importance` | 0 to 3, derived from how often the concept is taught and tested; drives node size |
| `ext.mesh`, `ext.wikidata` | Optional external IDs, added only when matched confidently |

A concept page is assembled at build time from relations: its definition, the sections and slides that explain it, the questions that test it, flashcards, related concepts, 3D models, figures and resources. A section of the page is shown only when it has content.

## 3.7 Relation

| Field | Type | Notes |
|---|---|---|
| `id` | string | Hash of `src`, `type`, `dst` (so the same link cannot be stored twice) |
| `src`, `dst` | record IDs | |
| `type` | string | See below |
| `origin` | `imported` · `ai` · `admin` | `imported` = already explicit in Sina's data |
| `confidence` | 0 to 1, optional | For AI suggestions |
| `rationale` | string, optional | Why the link is proposed, quoting the source where possible |
| `status` | `proposed` · `approved` · `rejected` | |
| `provenance` | array, optional | Slide or page supporting the link |
| `created`, `updated`, `reviewed_by` | | |

Relation types:

| Type | Typical use |
|---|---|
| `part-of` | lecture → module → subject; section → lecture; slide → source |
| `covers` | lecture or section → concept |
| `explains` | section, slide or resource → concept |
| `tests` | MCQ or flashcard → concept |
| `appears-in` | MCQ → lecture or paper |
| `cites` | MCQ or section → slide (exact provenance) |
| `related-to` | concept ↔ concept (symmetric) |
| `depends-on` | concept → prerequisite concept |
| `is-a` | concept → broader concept |
| `located-in`, `supplies`, `innervates` | anatomy-specific concept links |
| `causes`, `treats`, `presents-with` | clinical concept links |
| `contradicts` | two records that disagree (e.g. lecture versus external reference) |
| `references` | record → resource or article |
| `derived-from` | AI artifact or record → the record it was generated from |
| `duplicate-of` | Candidate duplicate awaiting a merge decision |
| `custom:<name>` | Anything else |

Imported relations (`part-of`, `appears-in`, `cites` from Sina's own data) are approved on import because they are explicit in the source. AI-suggested relations always start as `proposed`.

## 3.8 AI artifact

| Field | Notes |
|---|---|
| `target` | Record ID the artifact is about |
| `kind` | `summary` · `classification` · `keywords` · `concept-extraction` · `relation-suggestions` · `explanation` |
| `content` | The output |
| `model` | Model identifier used |
| `prompt_version` | Version of the instruction set |
| `input_hash` | Hash of exactly what the model was given |
| `created` | |
| `status` | `proposed` · `approved` · `rejected` |

`target + kind + prompt_version + input_hash` identifies an artifact. If nothing changed, the pipeline skips the item. This is what prevents paying twice for the same work.

## 3.9 Source and slide

Source: `id`, `title`, `mime`, `bytes`, `sha256`, `pages`, `drive_id`, `url`, `lecture`, `retrieved`.

Slide: `id`, `source`, `n` (page number), `image` (URL of Sina's slide image), `text` (OCR or extracted text), `lines` (text with bounding boxes), `text_origin` (`pdf-text` · `ocr` · `none`).

Original files are not copied into this repository. The record keeps the hash, so a changed or replaced file is detected on the next run.

## 3.10 Admin data

- `kb/admin/manifest.jsonl`: one line per ingestion item with its state (see [04-ingestion.md](04-ingestion.md)).
- `kb/admin/id-registry.jsonl`: every ID issued.
- `kb/admin/audit.jsonl`: append-only log of approvals, rejections, edits and merges (`when`, `who`, `action`, `ids`, `note`). Git history is the second audit trail.
- `kb/admin/stats.json`: generated coverage statistics.

## 3.11 File layout

```
kb/
  sources/<subject>/sources.jsonl
  sources/<subject>/slides.jsonl
  records/hierarchy.jsonl
  records/<subject>/lectures.jsonl
  records/<subject>/sections.jsonl
  records/<subject>/mcqs.jsonl
  records/<subject>/flashcards.jsonl
  records/concepts.jsonl
  records/papers.jsonl
  records/resources.jsonl
  relations/imported/<subject>.jsonl
  relations/curated.jsonl
  relations/proposed/<subject>.jsonl
  ai/<subject>/<kind>.jsonl
  admin/…
schemas/*.schema.json
```

One record per line, sorted by ID, so diffs are small and merges are clean.

## 3.12 Personal data (browser)

IndexedDB database `sina-brain`, with object stores for `notes`, `bookmarks`, `tasks`, `ideas`, `collections`, `annotations`, `uploads`, `plans`, `progress` and `settings`. Personal records refer to shared records by ID. Sina's own progress stays where it is and is read, not copied.

Export produces one JSON file containing all stores, with a format version. Import merges by record ID and keeps the newer of two versions.
